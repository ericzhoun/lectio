How should the Bible open?

Design preview for the inspire Bible-mode reveal flow · moment A (click) + moment B (arrival)

How to review: every demo auto-plays when it scrolls into view — hit ↻ Replay anytime. Pick your treatments in the Decisions section at the bottom and press Queue this answer, then use Send to Agent in the Lavish toolbar. Free-form annotations on anything are welcome too.
Goal

Make the Bible visibly open — today the most important visual beat in Bible mode doesn't exist.

Today

A static closed-book button submits instantly; a "please wait…" label covers the server round-trip; the finished reading page just appears after reload.

Direction (C)

Both ends. The book opens at the click (Moment A) while verses are drawn, and the reading page arrives by opening (Moment B).

Current flow

closed book (static)→ click, instant submit→ "please wait…" text→ page reload→ finished page

Proposed flow

closed book (static)→ A · book opens at the click→ server draws verses (hidden)→ B · reading page opens on arrival→ reading

Moment A — the click

What happens in the half-second after "Flip open the Bible" is pressed, while the server draws the verses. Three treatments.

A1 · Cover Swing

fastest

The front cover swings around the spine in real 3D, gold light spills from the seam, and the first page brightens underneath. One clean tactile beat — reads as "you opened it", not as a special effect.

Moment B — the arrival

How the cream reading page (the pending view you already have — only the entrance is new) reveals itself on load. Two treatments.

B1 · Spread Open

✓ Chosen

The closed book opens and dissolves into the reading page: the spread widens from the spine, the chapter heading drops in, verses fade up line by line, and the drawn verse gets a gold highlight sweep. The book literally becomes the page you read.

~2.7sclip-path unfold + staggerlow-medium cost
✝

B2 · Page Rise

quietest

No book metaphor — the reading page simply rises into place with a soft gold light sweep and the same staggered text. The fastest and most conservative option; ages well and never blocks reading.

~1.8ssimplestvery low cost

How it maps to the code

  • Moment A → index.astro #bible-flip-btn / .bible-flip-panel: replace the static .bible-flip-book span with the 3D scene. On click, play the page cascade and submit ~1.8s later (as the second page lands) — with cinematic pacing the full ritual runs ~2.9s, so the veil and arrival unfold carry the tail. Existing zh/en labels unchanged.
  • Moment B → .bible-page (pending + result views): add an arrival class on render; keyframes live in global.css. Interpret bar and reveal-gate UI untouched.
  • Reduced motion → the same prefers-reduced-motion path swaps everything for a 200ms cross-fade.
  • No dependencies — all effects are CSS keyframes plus ~40 lines of JS to trigger, reset and sequence them. No libraries, no images.
  • Latency masking — A plays while the server draws; the "please wait…" label disappears because the animation is the wait.
  • Freemium flow intact — anonymous visitors still see the verses free; the registration gate on 解经/reveal is untouched.

Risks & open questions

  • Navigation cut. The form POST navigates as soon as the server answers (~0.2–0.6s). With the chosen A3 cascade at cinematic pacing, submit ~1.8s in (as the second page lands) — the veil and arrival unfold carry the rest of the ritual on the next page.
  • Glow performance. All glows animate opacity only — never filter: blur(). A2 is the most expensive; if low-end phones struggle, A1 degrades gracefully.
  • Repeat replays. The arrival animation fires on every page load, including back/refresh. A once-per-session guard (sessionStorage) is cheap if it ever feels repetitive — see Q5.
  • Old Android WebView. 3D transforms degrade to the reduced-motion fade path — acceptable.
  • Open: should Moment A also apply to registered users? Recommended yes — it's the same button flow for everyone.
