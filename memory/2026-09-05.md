## Chatterbox prebuilt TTS pipeline for Lectio
- Decisions from the user: prebuilt-at-build-time, free for everyone; audio wanted for passage, AI reflection, step prompts, whole session.
- Built scripts/tts/ (synth.py + lib.mts + steps.mts + passages.mts) driving the local Chatterbox venv at D:\workplace\TTS\chatterbox\.venv (ChatterboxMultilingualTTS, cuda, exaggeration 0.3 cfg 0.5, default voice).
- Key measurements: T3 decoder caps one generate at ~40s audio; en ~19 chars/s, zh ~2 chars/s (contemplative). synth.py chunks (en 450 / zh 90 chars) and joins with 0.35s gaps; WAV 24kHz -> ffmpeg mp3 48k mono.
- Steps: `npm run tts:steps` -> public/audio/steps/<lang>/<step>-<hash8>.mp3 (12 clips, ~3 min GPU); manifest src/lib/audioSteps.json; orphan cleanup; hash-skip makes reruns free.
- Passages: `npm run tts:passages -- --next N | --from D --days N | --all --yes`; resumable (skip existing mp3s), manifest src/lib/audioDays.json rebuilt from disk. Full 1826-day x 2 backlog is a long-running offline job (~2.5 min/clip measured -> weeks of part-time GPU); rolling-window workflow is the intended usage.
- App: /api/tts serves prebuilt asset via env.ASSETS when the manifest lists the day, else MeloTTS on demand (unchanged fallback). [step].astro: guidance clip button in header, prebuilt-first Listen button, AI reply button (POST /api/reflection-tts), guided-session playlist player on silencio (7 items incl. passage, pauses 50/6/10/90/90/110s, never navigates).
- reflection-tts endpoint speaks ONLY ai_text from D1 for the session's pinned lang - no arbitrary request text, per the existing cost rule; per-reader so private/no-store (not in shared Cache API).
- env.d.ts: added ASSETS binding type. public/_headers: long cache for /audio/*. .gitignore: .tts-work/. devDep tsx for scripts importing src/lib TS modules.
- Verified: astro check 0 errors; vitest 268 pass (incl. new audio.test.ts); ASR round-trip on zh Matt 1:18 + step clips - homophone-only diffs (whisper picked 送毒/宣銷 for 诵读/喧嚣).
- Gotcha: scripts import src/lib/*.ts which import JSON without `with { type: 'json' }` attributes, so plain Node type-stripping cannot load them -> tsx devDep is required for the tts scripts.

## --engine kokoro added to the TTS batch pipeline + full-table backlog run
- passages.mts now takes --engine chatterbox|kokoro (default chatterbox). lib.mts synthesize() picks the worker: scripts/tts/synth_kokoro.py (same JSONL protocol) under the kokoro venv. Voices: en=af_heart, zh=zm_yunxi. Manifest audioDays.json gained an "engines" map (per lang/day provenance; pre-kokoro files default 'chatterbox').
- Kokoro venv moved to CUDA: torch 2.14.0+cpu -> 2.6.0+cu124. Gotcha: `--torch-backend=cu124` alone did nothing for torch 2.14 (uv keeps installed version; cu124 builds stop at 2.6) - install explicit `torch==2.6.0` with the backend flag. 2.14 has no cu128 Windows wheel either.
- BUG caught in the wild: `days.filter(...).sort()` after the --all branch silently re-sorted away the future-first ordering (run was chewing through Jan 2026). Fixed: filter only. Lesson: verify background batch by watching .tts-work wav filenames, not the buffered log.
- lib.mts now encodes each clip with ffmpeg the moment the worker emits done (incremental), so an interrupted run loses at most one clip; before, all mp3s landed only at the end.
- Measured kokoro on RTX 3080: ~1.3 s/clip including encode (30-40x realtime) vs chatterbox ~2.6 min/clip. Full 1826x2 backlog ETA ~80 min. run_tts_backlog.bat = standalone resumable runner.
